# Pier API integration
Authenticated Base native session, same-origin JSON POST. GET `/api/pier/state` returns `{version,actor:{id,name,role},items,locations,parties,supplierItems,orders,purchaseOrders,receipts,transfers,shipments,returns,counts,proposals,imports,receivings,carriers,waves,packs,dispatchDays,positions,movements,reservations,commands}`. Arrays use camelCase. Decimal quantities/costs are strings (6 fractional places maximum); IDs are UUID strings. No seeded records. GET `/api/pier/export` returns complete business data JSON. POST `/api/pier/commands` body `{commandId:crypto.randomUUID(),type,payload}` returns `{ok:true,result,version}`; failures `{ok:false,error:{code,message,details}}` (400/401/403/409). Repeat SAME commandId and payload recovers original outcome. Command types/payloads:
- `item.save`: `{id?,sku,name,barcode?,caseBarcode?,unit,packSize:"1",archived?:false,version?}` (a `caseBarcode` scan counts one pack of `packSize` base units). `location.save`: `{id?,name,warehouse,kind:"bin"|"transit",barcode?}`. `party.save`: `{id?,name,kind:"supplier"|"customer"}`. `supplierItem.save`: `{id?,supplierId,itemId,code,packSize,price,minimum,leadDays,version?}`.
- `order.create`: `{customerId,promiseDate?,channel?,lines:[{itemId,quantity,price?}]}` atomically reserves across sellable bins; result is order. `order.reserve`: `{orderId}` reserve backorder after new receipt. `order.cancel`: `{orderId,reason}` cancels ALL remaining unshipped demand.
- `po.draft`: `{supplierId,promiseDate,lines:[{itemId,quantity,price}],reason,freight?,duty?,tax?}` -> PO draft. `po.revise`: `{poId,version,supplierId,promiseDate,lines,reason}`. `po.approve`: `{poId,version}` -> approved exact snapshot. `po.commit`: `{poId,version}` -> expected stock. `receipt.create`: `{poId,supplierReference,currency?:"USD",usdRate?,landedCost?:{freight:"0",duty:"0",insurance:"0",other:"0",allocation:"value"|"quantity"|"weight"},lines:[{poLineId,locationId,quantity,cost}]}` -> receipt. `receipt.reverse`: `{receiptId,reason}`.
- `transfer.send`: `{itemId,fromLocationId,toLocationId,transitLocationId,quantity,reason}` -> transfer. `transfer.receive`: `{transferId}` confirms full transfer.
- `dispatch.create`: `{orderId,shipmentReference,lines:[{orderLineId,quantity}]}` -> shipment consuming own reservations. `return.create`: `{shipmentId,shipmentLineId,locationId,quantity,reason}` -> quarantined return. `return.approve`: `{returnId,version}` then `return.restock`: `{returnId,version}`.
- `count.capture`: `{locationId}` -> count with captured lines `{itemId,status,expected,quantity}` and frontier. `count.record`: `{countId,version,lines:[{itemId,status,quantity}],reason}`. `count.approve`: `{countId,version}` posts exact adjustment or fails stale frontier. `count.recount`: `{countId}` captures a new count.
- `proposal.prepare`: `{kind:"replenishment"|"reallocation"|"count-drift"|"migration",assumptions,evidence:[string],plan:object}`. Agents can draft POs and proposals, never approve or post. Replenishment automatic read context exposed in GET state `reorder`. `proposal.approve`: `{proposalId,version}`. `proposal.execute`: `{proposalId,version}`; reallocation plan `{fromOrderId,toOrderId,itemId,quantity}`, count-drift plan `{countId,version}`; other proposals retain human-reviewed preparation and use ordinary PO/import commands for exact commitment.
- `import.stage`: `{namespace,sourceVersion,exportedAt,filters,cutoffTimezone,currency?:"USD"|ISO 4217,conversionRates?:{AUD:"0.65"},mappingRevision:"1",files:[{name,kind:"items"|"locations"|"parties"|"positions"|"orders"|"purchaseOrders"|"reservations",csv}]}`. `reservations` is optional and preserves exact per-line/per-bin allocation, including explicit zero backorders; when present, include all open lines of each affected order. Each request accepts 1–20 files, at most 1 MiB UTF-8 and 1,000 data rows per file; text-validated names and values have a 2,000-character limit, and decimal fields allow up to 10 whole digits and six fractional digits. Native exact headers and rules are in `IMPORT.md`. -> batch with original files, rows/errors,reconciliation,status. `import.review`: `{batchId,version,stage:"mapped"|"reconciled"|"shadow"|"frozen",reason}`. `import.commit`: `{batchId,version}`. `import.undo`: `{batchId,version,reason}`.
- Warehouse floor (role `warehouse`; a code is a scanned or typed barcode, bin name or SKU; numeric retail codes compare as GTIN-14). `receiving.start`: `{poId,locationId}` -> open scan tally on a committed PO. `receiving.scan`: `{receivingId,code,count?}` adds one unit, one case or `count` scans; a bin code moves later scans to that bin; unknown or off-PO codes are refused with no effect. `receiving.remove`: `{receivingId,scanId}`. `receiving.post`: `{receivingId,version,supplierReference,overReason?}` -> receipt into the scanned bins with `variance:[{poLineId,itemId,expected,received,over,short}]`; over-receipt needs `overReason`, short lines stay expected. `carrier.save` (operator or warehouse): `{id?,version?,name,warehouse,dock,cutoff:"HH:MM",timeZone}`. `order.carrier`: `{orderId,carrierId,shipByDate?}`; optional reviewed carrier-service date is valid `YYYY-MM-DD`, `null` clears it, omission preserves it, and actor/time are retained. `wave.release`: `{carrierId,orderIds}` -> wave `{number,dock,orders:[{orderId,tote}],lines:[{id,orderId,orderLineId,itemId,locationId,quantity,picked,status}]}` in bin pick sequence from each order's own reservations. `pick.scan`: `{waveId,lineId,binCode,itemCode,quantity?}` refuses `WRONG_BIN`, `WRONG_ITEM`, `UNKNOWN_CODE` and `OVER_PICK` with the reason. `pick.short`: `{waveId,lineId,reason?}` moves only that line's unpicked reservation to the next bin in pick sequence holding unreserved stock (a new overflow line), releases what no bin holds and opens a count of the reported bin. `pack.scan`: `{waveId,orderId,code}` into the open carton (refuses more than was picked). `pack.carton`: `{waveId,orderId}`. `pack.measure`: `{waveId,orderId,carton,weight,length,width,height}` (lb, in). `pack.close`: `{waveId,orderId}` marks packed when every picked unit is in a measured carton. `pack.dispatch`: `{waveId,orderId,shipmentReference}` dispatches the packed units through `dispatch.create`. GET `/api/pier/dispatch-summary?date=YYYY-MM-DD&timeZone=&warehouse=` -> per-state due-order counts/lists, pickup schedules and conservative pre-cutoff risks, plus the day's orders, shipments and units shipped, by carrier and dock against each cut-off, and exceptions (due orders not shipped with the reason, short picks, shipments after cut-off, receipts over or short). `dispatch.close`: `{date,timeZone,warehouse?}` keeps that summary (earlier closes survive in revisions) and sends the owner a copy through the installation's mail; the record's `delivery` says whether it was sent.
- `role.set`: `{operatorId,role:"owner"|"buyer"|"operator"|"warehouse"|"viewer"|"agent"}` owner only, using native invited operator ID. GET state `operators` available owner.
State entities preserve ids and version. Order line has id,itemId,quantity,dispatched,cancelled,reserved,backorder. PO line id,itemId,quantity,price,received. Position itemId,locationId,status (`sellable`/`quarantine`/`transit`),quantity,reserved,available. All actions send decimal strings, never floating numbers. Tables show API errors visibly; expose forms for every flow, review and provenance rather than fake examples.

`import.revise`: `{batchId,version,decisions:[{kind,key,action:"replace"}],reason}` explicitly reviews changed-source replacement, including `kind:"reservations"`, then restarts reconciliation. `receipt.correct`: `{receiptId,countId,version,reason}` posts an exact reviewed physical-count correction linked to the receipt. See IMPORT.md for graph publication/undo. Raw movements.quantity and top-level reservations.quantity are integer millionths; shipment reservation links are base-unit decimals. GET `/api/pier/native-export` returns the six established CSV files plus `reservations.csv`, cutoff metadata and separate receipt-cost evidence.

Import preview, each review stage and commit check the actual byte-bounded D1 SQL, the retained import record and its successful command result. When a retained record or result exceeds the 2,000,000-byte D1 value budget after source, reconciliation, review and provenance are included, the command returns `IMPORT_SIZE` and posts no stock. This is not a cap on the raw sum of source CSV bytes; split oversized imports into separately staged and reconciled batches. Native graph writes are chunked by encoded bytes so a large aggregate row count is not rejected solely for its total size.

## Prices, costing and reports

`priceList.save` accepts `{id?,version?,customerId,itemId,minimumQuantity:"0",price,validFrom?,validTo?}`. Buyers, sales operators and owners maintain versioned USD price tiers. Inclusive validity dates use UTC. A new order with an omitted price takes the highest eligible quantity tier, then the most recent effective date; supplied prices override the list. Orders snapshot their source and exact extended totals with twelve fractional places. Unpriced lines have null price/total, never an invented zero. Edits to a price list leave existing orders unchanged. `channel` defaults to `manual` and is a recorded order source, not proof of a channel connector.

Receipts retain source currency, source unit costs, exact source totals and the reviewed USD rate with actor and timestamp. Non-USD receipts require an explicit positive `usdRate` (one source-currency unit in USD). The operational USD unit cost uses the existing six-place conversion; source precision remains readable. Freight, duty, insurance and other landed charges are whole-cent USD amounts. Reviewed value, quantity or weight allocation uses largest remainders so every charge sums exactly to its entered total. Weight allocation requires positive per-unit pounds on every item and captures those weights on the receipt; later catalogue edits do not alter them. Use `landedTotal` for reconciliation; unit cost is a rounded display amount.

Owners approve a supplemental bill with `receipt.landed`: `{receiptId,version,supplierId?,reference,reason,landedCost:{freight,duty,insurance?,other?,allocation}}`. The optional supplier is the actual issuer of the late bill; omission selects the PO supplier. Its reference is unique for that supplier. Approval preserves the original receipt lines and physical movements, retains per-line shares, and computes supplemental inventory, net COGS and mapped removed-stock expense. A separate payable and balanced journal use stable source identities. Original cost documents keep their baseline amounts, including documents not sent yet. Unbuilt baseline journals and prior adjustments without a mapped expense require review. A receipt with approved late bills cannot be reversed through the physical receipt-reversal door. The recorded bill date is its approval date; earlier as-of reports exclude later bills.

In Books settings, the owner saves `writeOffAccountId`, `writeOffReasonCode` (default `damaged`) and `writeOffApprovalLimit` (default zero USD) through `book.connect`. Each code retains its mapped account, limit and approval; saving a code updates that code and preserves other codes. A damaged `return.scan` or `return.inspect` chooses `reasonCode` (the sole code is the default). Amounts strictly above the code limit require owner authority and explicit `approveWriteOff:true`. Missing mappings or unvalued units refuse the write without stock effects. The return snapshots the code, exact consumed cost, account and approver; later mapping changes leave existing postings intact. Existing connections without a reason mapping must be reviewed in Books settings before another write-off.

Owners call `costing.method` with `{method:"fifo"|"average",reason,confirm:true}`. FIFO is the initial policy. Changes record the server timestamp, actor and movement frontier, preserve past shipment costs and apply prospectively to remaining stock. Moving average pools USD cost per SKU across owned locations; transfers preserve value. Changing back to FIFO retains the current values and receipt sequence. There is no backdating.

Authenticated `GET /api/pier/reports?asOf=YYYY-MM-DD&from=YYYY-MM-DD&to=YYYY-MM-DD&days=180` returns USD valuation, operational reconciliation, shipment margin grouped by SKU/channel/customer and dead stock. Dates are inclusive UTC days. Stock includes sellable, quarantine and transit; reservations remain owned stock. Margin is actual shipped quantity at saved order prices less consumed cost, excluding tax and financial credits/refunds. Dead stock lists SKU/bin stock with no sale shipment or transfer out in N days and shows value, last sale and last movement. API valuation rows expose remaining source layers; CSV downloads retain exact monetary strings and report parameters.

Unknown USD costs, legacy receipts without an explicit USD currency, non-USD opening imports without a recorded rate and unpriced orders stay explicitly incomplete. Physical returns restore the dispatched line's cost but do not issue financial credits. Uncosted count gains require review; they do not acquire a guessed cost. Native Pantry reconciliation includes receipt FX and supplemental landed bills. Fractions of a cent at a payable boundary and provider period-lock refusals enter the Books review queue; no automatic date substitution or silent accounting rounding occurs. QBO and Xero connections, imported sales history and wider reports retain their own contract obligations.

## Replenishment and correspondence

`GET /api/pier/state` includes `forecasts`, each order’s `backorderPlan`, expected PO landed costs, approved `correspondence`, and provider `deliveries`. `replenishment.save` reviews a per-item/warehouse policy; `applyLearned: true` requires its exact `stateVersion`. `replenishment.plan` creates supplier/destination drafts without approval. `po.send` requires a committed exact `version`, `recipient`, `confirm: true`, and bounded `chaseEveryDays` / `maxChases`. `po.reply` retains a supplier `source` and `body`; `po.confirm` additionally approves a `promiseDate` with `confirm: true`. `po.pauseChases` revokes future reminders. `order.repromise` requires the current `backorderPlan.fingerprint`, exact order version, recipient and approval. `order.promisePolicy` enables or revokes order-specific automatic date messages. `mail.process` submits due approved messages, never resubmitting an uncertain claim. See [Replenishment](docs/replenishment.md).


## Sales channels

See [Sales channels](docs/channels.md). Owner commands through the existing authenticated command door are `channel.save`, `channel.sync`, `channel.match`, `channel.hold` and `channel.release`. Configuration includes a provider (`stall`, `woocommerce`, `shopify`, `amazon`), `name`, `baseUrl`, `warehouse`, decimal-string `buffer`, `enabled` and provider-specific `credentials`; updates include `id` and current `version`. Omit credentials on update to retain them. State includes channels, listings with published/available quantities and lag, source orders with native order IDs, and transfer holds. Credentials never appear in that state or business exports.

`channel.match` takes `listingId`, `version`, `itemId`; `channel.hold` takes `itemId`, `warehouse`, `quantity`, `reason`; `channel.release` takes `holdId`, `version`. A WooCommerce connection with a webhook signing secret accepts signed POST notices at `/api/pier/channels/CONNECTION_ID/webhook` without a browser session; the signature grants only canonical reconciliation, not arbitrary stock commands. Internal connector result commands are refused at the public command door.

## Books

Financial transport commands are internal. Books collections in state/export retain source identity, attempts, remote IDs, reasons, paid/open amounts and receipt evidence status. Buyers/owners approve with `supplierBill.approve` (`id`, `version`, the exact current `match.receiptEvidence`) or hold with `supplierBill.hold` (`id`, `version`, `reason`). Only Pantry payment readback produces paid status.

Service ship-by dates are explicitly reviewed inputs; carrier-service inference remains pending under SHIP-001.

## Supplier performance (BUY-004)

Current supplier scorecards are available through authenticated `GET /api/pier/supplier-performance`. They group by supplier and SKU/base unit, never total unlike units. Fill is gross unreversed posted receipt quantity divided by current committed PO quantity (including open commitments); over-receipts are visible as excess and can exceed 100% fill. On-time is received quantity on or before the supplier-confirmed date, divided by receipt quantity with a retained confirmation, comparing inclusive UTC calendar days. Both receiving doors snapshot the approved confirmation and supplier reply at posting; later confirmations do not rewrite earlier receipts. Missing or legacy confirmation evidence is unknown and excluded only from the on-time denominator; reversed receipts are excluded from every quantity but remain cited. Percentages truncate to six decimals, with a null zero-denominator rate. Receipt quantities, cost-versus-PO unit-price differences, source IDs and count-correction links remain inspectable. Stock corrections and customer returns do not establish supplier defects. `receipt.inspect` (`receiptId`, `lines: [{receiptLineId, inspected, defective, defect}]`; `defect` is required when `defective` is above zero) appends a finding to a posted receipt line, capped at its received quantity, moving no stock; items report `inspectedQuantity`, `defectiveQuantity`, `uninspectedQuantity` and `defectPercent` (null when nothing is inspected).

The response returns `suppliers[].items[]` with exact decimal quantities and percentages, `purchaseLines` and `receipts` as source evidence. Each receipt includes its `inspections`, retained confirmation/reply, timing (`on-time`, `late`, `unknown` or `excluded`), exclusion reason, quantity and unit-price difference. This read-only endpoint follows the existing signed-in read door and writes no stock or command result. No screen or full supplier-rating workflow is claimed.


## Warehouse placement and slotting (WMS-002)

`location.policy` (owner) takes `{locationId, version, capacityCm3, lengthCm, widthCm, heightCm, aisleMetres, bayMetres, pickSequence, allowedItemIds:[], pickFace:false, pickFaces:[{itemId,minimum,maximum}]}`. Measurements and thresholds are decimal strings; all item dimensions must be known before stock occupies a configured bin. The owner acts for the missing supervisor role. This changes no stock and cannot validate an already overfilled bin.

`slotting.plan` (warehouse or owner) takes `{warehouse, sourceLocationId?}`. The optional source is the receiving bin to put away. The returned/exported plan retains prioritized tasks and ABC source observations without moving stock. `slotting.approve` (owner) takes `{planId,version}`. `slotting.scan` (warehouse or owner) takes `{planId,version,taskIndex,fromCode,toCode,itemCode,quantity,device}`; `taskIndex` is the zero-based task index and `quantity` is the exact approved decimal base-unit quantity. It rechecks current approval authority, item/bin versions, stock reservations and total capacity, then posts the paired internal movements atomically. Retry a lost response with the same command ID and payload. A different command cannot complete a task twice.

The Transfers screen exposes policies, planning, approval and physical confirmation. See [Warehouse placement](docs/warehouse-placement.md) for measurements and recommendation semantics.

### Warehouse grants

Owners may add `permissions: {warehouses: ["North"], locationIds: []}` to `role.set`. A nonempty location list narrows the listed warehouses; an empty warehouse list grants no physical positions. The conservative scoped door currently supports physical stock reads, `GET /api/pier/scope-export` and count commands only. It excludes costs, prices, parties, commercial documents, connections, other operators and command results. Other private read/export/command doors refuse scoped actors. Omit `permissions` to retain the existing global role behavior. The current role-record version is fenced inside atomic admission: changing a grant while retaining the same role revokes the prepared operation. Invites do not carry a grant; restored role rows are viewer evidence until a fresh owner grants access. Broader scoped warehouse workflows and fine roles remain ADMIN-001 gaps.

### Retention and attachment erasure

`GET /api/pier/privacy` is owner-only and lists retention reviews, legal/accounting holds and value-free completion receipts. `GET /api/pier/privacy?kind=attachment&subjectId=ID` previews local original/extraction/raw-inbox counts and holds, with a current `planHash`. Customer/supplier/operator previews are inspection-only and explicitly cannot erase those subjects yet.

`privacy.hold` takes `{kind,subjectId,category:"legal"|"accounting",reason,active}` and optional `{id,version}` when releasing/changing a hold. `privacy.retention` takes `{version,reviewAfterDays,automaticDeletion:false,reason}`: this sets a UTC review date, never a destructive scheduler. `privacy.eraseAttachment` takes `{documentId,planHash,confirm:true}`. It refuses changed dependencies, legal/accounting holds and unfinished extraction requests. On explicit approval, it erases the selected original, derived extraction drafts, containing raw inbox copies and recoverable command replies in one atomic admission with an archive redaction checkpoint. Stock, approved commercial records and opaque provenance remain; this is attachment erasure, not complete subject erasure. An older archive plus the later erasure-journal archive is refused rather than resurrecting private data. Offline copies and delivered/provider-held messages remain outside local deletion. This conservative retention/custody default awaits ct approval under DATA-002.

### Controlled native workflows and saved reports

Owners use `workflow.save` with `{name,kind:"inventory-check"|"draft-po"|"report",warehouses,supplierIds,perRunBudget,dailyBudget,cadenceMinutes,automaticApproval:false}` and optional `{id,version}`. Saving disables the rule. `workflow.preview {ruleId,version}` returns exact evidence and a `previewHash`; `workflow.enable` requires that current hash and version. `workflow.pause` and `workflow.kill` require the exact version. A killed rule cannot be edited or re-enabled. Purchases remain unapproved drafts: workflow rules cannot approve, post stock or send externally. This conservative delegation default awaits ct under AUTO-002.

`workflow.enqueue {ruleId}` prepares one job per rule/version/UTC cadence window. `workflow.claim {ruleId,jobId,version}` reserves expected landed spend against both the run and UTC-day budget; uncertain jobs keep their budget reserved. `workflow.finish` checks that exact rule version and source evidence before atomically producing its result. Changed or excess work becomes failed with a visible human-review reason. `workflow.recover {}` escalates expired running leases to uncertain without replay. Cron runs at most ten currently authorized rules per invocation; every attempt/outcome remains in business export and Activity.

`report.save {name,parameters}` saves exact supported date, warehouse, customer, channel and variant-family parameters; `report.run {reportId,version}` retains an immutable snapshot. `report.schedule {reportId,version,cadenceMinutes,enabled,confirm:true}` explicitly authorizes private scheduled snapshots, never email. Editing an analysis invalidates its old scheduled definition. `GET /api/pier/report-snapshots/ID.csv` exports the exact retained valuation, shipment margin and dead-stock rows. Filters and basis remain in the snapshot. Scoped grants cannot use financial report or saved-snapshot doors. Full report definitions and measured capacity remain REPORT-001/002 and SCALE-001 work; the UI states that capacity is unmeasured.

### Explicit credit posting

- `dropship.postCredit`: `{dropshipId, version, creditId}`. Owner only; requires connected Pantry and an unposted retained credit for that dropship. Authorizes its direct shipment invoice and linked native customer credit note, with no stock or cash effect. A repeated command identity recovers its saved outcome; another authorization is refused with `CREDIT`.
- `supplierReturn.postCredit`: `{returnId, version, reference, supplierBillId}`. Owner only; selects an unposted retained supplier credit and an approved payable whose matching covers the original returned receipt quantities. Posting allocates the credit to that Pantry bill and reads back the allocation. A duplicate authorization, wrong payable or excessive matched credit quantity is refused with `SUPPLIER_CREDIT`. Missing connection is `BOOK_CONNECTION`; stale versions are `STALE`; unauthorized callers get 403 `FORBIDDEN`. Provider scope, period, balance and reconciliation refusals remain visible in Books; an uncertain request is never silently reported posted. Reuse each original command identity after a lost response; changing its body gets 409 `IDEMPOTENCY`.


## Purchase approval limits and supplier changes

The owner configures native purchase routing with `purchaseApproval.save`:

```json
{"version":0,"limits":[{"supplierId":null,"exceptionType":"any","maxSpend":"1000","approverId":"named-current-buyer-id","escalationId":"named-current-owner-id","delegates":[]}]}
```

Use the saved policy version for each edit. `supplierId: null` is the general scope; a supplier ID restricts that limit. `exceptionType` is `standard`, `minimum-order` or `any`. Each delegate is `{actorId,expiresAt}` with a future ISO UTC timestamp. Limits include supplier tax as well as goods, freight and duty. Supplier specificity wins before exception specificity, then the lowest inclusive covering ceiling wins. There is no fallback past a more specific scope with insufficient spend authority. A policy edit clears previous PO approvals and stops pending send grants. Before any policy exists, the established current-buyer approval door remains in effect.

`po.routeApproval` takes `{poId,version}` and records the current named route; state reads also project it as `approvalRoute` or `approvalRouteError`. `po.escalateApproval` takes `{poId,version,reason}` and requires an owner; it selects the configured escalation approver for the current draft or committed purchase. Neither command approves or sends. Existing `po.approve`, `po.commit`, `po.authorizeSend`, `po.sendApproved`, `po.send` and purchase-order `print.send` enforce current routing. All purchase sends retain and attach a PRINT-001 PDF and share duplicate suppression.

`po.supplierChange` takes `{poId,version,source,body,promiseDate?,destinationWarehouse?,lines:[{poLineId,quantity,price}]}`. Include every original line exactly once, using base quantities and USD prices. It retains the supplier evidence, stops sends and chases and clears approval, leaving committed values unchanged. Further evidence supersedes the pending proposal while preserving earlier intake. `po.reviewSupplierChange` takes `{poId,version,confirm:true}` and requires the current routed human approver. It applies the retained proposal, preserves original commitment history and current receipt totals, and refuses quantities below already received goods. Zeroing every unreceived line cancels the purchase. A changed supplier price can require a higher approval tier. Receipt progress during review is checked again before applying.

`po.confirm` remains the explicit human date-confirmation door; `po.reply` retains acknowledgments. Reviewed supplier ASN intake remains `receiving.notice` followed by the confirmed SSCC receiving command. A timeout or uncertain mail outcome is retained for reconciliation; neither a fresh command identity nor scheduled mail processing silently retries it.
